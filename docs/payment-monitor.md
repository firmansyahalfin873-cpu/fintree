# Payment monitor — development draft

`runScannerCycle` scans a configured contract and chain using a trusted RPC provider. Its private database checkpoint records the next block to inspect. A lease prevents two workers from advancing the same checkpoint at once, and each cycle rechecks transactions that are waiting for confirmations. Blocks immediately before the checkpoint are rescanned to improve recovery from short reorganizations. Failed or unresolved scans do not advance the checkpoint.

`runScannerLoop` runs one cycle at a time and retries failures with bounded backoff. A cycle marks overdue pending invoices expired in bounded batches; a valid payment made before the deadline can still be reconciled if discovered later. If a previously confirming transaction is re-included in another canonical block but no longer contains a valid payment, its stale confirmation is cleared and the invoice returns to pending or expired. The application that starts the monitor must persist the database, supply a trusted provider and deployment block, choose the required confirmation count and rescan overlap, stop the loop on shutdown, and report errors to an operator. The scanner must run independently of the buyer's browser.

The monitor also rechecks paid invoices in bounded batches. If the canonical block hash at a payment's recorded block changes, it atomically records an incident and queues `checkout.session.payment_review_required` once. The existing `paid` status is preserved for audit, while merchant and public checkout responses set `reviewRequired: true`; the interface asks for manual review. An RPC that is behind the payment block or returns no block does not by itself create an incident. This detects a changed block, not whether the same payment was later re-included; an operator must investigate. Automatic incident resolution is not yet available.

The overlap and confirmation count are policy decisions, not guarantees against arbitrarily deep chain reorganizations or dishonest or inconsistent RPC providers. Detection is periodic and bounded, so it may be delayed. Operational alerts, incident response, and independent verification remain necessary. This prototype has been tested with a local EVM and local Postgres-compatible database; it has not been deployed or validated against a public network.
