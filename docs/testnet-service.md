# Local testnet service

This is a local development service for Base Sepolia only. It binds to `127.0.0.1`; it is not intended to be exposed to the Internet or used with mainnet funds. The browser preview (`npm run preview`) remains a separate, fully simulated experience.

The experimental browser-wallet setup described in [deployment preparation](testnet-deployment.md) can also start this service after a verified testnet deployment. That route unlocks separately encrypted signer and webhook keys locally and keeps its setup process running. Its wallet interaction and deployment have been tested only with a simulated chain so far.

Before starting `npm run testnet`, configure the environment variables listed in `.env.example`: an HTTPS Base Sepolia RPC URL, a test-only quote signer private key, a deployed splitter, the test token, and the splitter's deployment block. `FINTREE_WEBHOOK_MASTER_KEY` is optional; when present it must be a securely generated 32-byte key encoded as 64 hexadecimal characters and enables encrypted webhook settings and the delivery worker. Keep the same key across restarts: changing or losing it makes existing webhook secrets unreadable, and startup rejects an incorrect key. Store keys outside the database, back them up securely, and do not paste them into chat or commit them to files. Without the master key, webhook configuration and delivery stay disabled.

A testnet deployment has not been created by this project yet. The signer must match the splitter's configured signer, the token must match the splitter's configured token and have six decimals, and the RPC must identify as Base Sepolia. The service verifies these before accepting requests. See [deployment preparation](testnet-deployment.md) for the read-only checks and testnet deployment script.

The service stores test data under `.fintree-data/testnet` unless `FINTREE_DATABASE_PATH` is set. This database is intended for one local process. It keeps merchant records, test API key hashes, invoices and scan checkpoints across restarts. New databases are initialized at the latest known local schema. For an existing supported database, stop the service, make and verify a backup, then run `npm run db:migrate` using the same `FINTREE_DATABASE_PATH`; the command applies known pending local migrations in a transaction. It refuses unknown, modified, or newer schemas for manual review. Historical prototype schemas whose checksum is not in the known migration list are not automatically upgraded. These PGlite-specific local migrations are not Supabase migrations.

The service includes a testnet merchant page with a configurable business name, wallet-based onboarding, checkout sessions, a public wallet checkout page, and an HTTP API. Checkout validates the deployment and quote before requesting token approval or payment; it waits for server verification before showing a paid status. A background monitor scans from the supplied deployment block and currently uses a provisional 20-confirmation policy and a bounded reorganization overlap. When enabled, webhook delivery uses a restricted HTTPS transport and retries failed attempts. These controls have been tested with mock networking, not independently reviewed or verified against a real merchant endpoint. Operational alerts and production access controls remain incomplete. The page logic has been exercised with a simulated wallet and local chain; a public testnet deployment and its end-to-end behavior are not yet verified.

The dashboard can show whether the local payment-monitor and webhook-worker cycles are starting, running, delayed, or disabled. A running worker does not prove that the scanner is caught up, an invoice is paid, or a webhook reached its endpoint; check the invoice and delivery history for those results. Status is held in memory and resets when the service restarts. It is not an external uptime monitor or an alerting system.

Each successful wallet connection issues a new test API key. The merchant page lists key prefixes and can create or revoke keys; full keys are shown only when issued. Replace a key in any integration before revoking it. Revoking the key used by the current page ends that page's authenticated session; reconnect the wallet to obtain a new test key. Key-list pagination covers older keys and revoked entries.
